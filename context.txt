# Project Context Brief: Satellite Pass Scheduler for Ground Stations

## 1. Basics
- **Course/context:** Object-Oriented Programming (OOP) course mini project
- **Team:** 4 CS students
- **Language:** Java (other languages only where necessary)
- **Timeline:** 1-2 months
- **Working title (proposed):** OrbitSlot: A Multi-Algorithm Pass Scheduler for Satellite Ground Stations
- **Status:** Idea selected and being pitched to the teacher. No code written yet.
- **Requirement from the course:** the main concept need not be OOP, but OOP must be implemented meaningfully (class hierarchies, interfaces, polymorphism, design patterns).


## 2. Problem
A low-earth-orbit (LEO) satellite is visible to a ground station for only about 5-15 minutes per pass. A station has a limited number of antennas, and many satellites (weather, comms, cubesats) compete for the same windows. Each pass has limited downlink capacity. Bad schedules cause lost data, overflowing onboard buffers, and missed critical contacts. Small operators often plan by hand or in spreadsheets, which fails when passes overlap or get cancelled (rain fade, antenna fault, urgent satellite).

## 3. Solution
A Java system that takes satellites, pass windows, and station constraints, and produces an optimized, conflict-free antenna schedule.

Features:
1. **Pass prediction** from orbit data (TLE/GP) via a library, or simulated windows to limit scope.
2. **Constraint modeling:** priority, downlink data volume, antenna slew time between consecutive passes, onboard buffer limits, minimum elevation angle.
3. **Multiple swappable scheduling algorithms**, compared on identical inputs.
4. **Live re-planning:** local repair of the schedule when a pass is cancelled.
5. **JavaFX Gantt-style timeline:** antennas, passes, conflicts, dropped passes.
6. **Benchmark mode:** compares algorithms on the metrics below.
7. **Scenario generator:** reproducible random test cases, including cancellation events.

**Metrics:** total data downlinked, antenna utilization, number of high-priority passes missed.

**Stretch goals:** multiple ground stations, fairness between satellite operators, an ILP/constraint-programming comparison (e.g., OR-Tools).

## 4. Scheduling algorithms (planned lineup)
1. Baseline: first-come-first-served (to show why naive scheduling fails)
2. Greedy by priority
3. Weighted interval scheduling via dynamic programming (optimal for a single antenna without extra constraints)
4. Local search / simulated annealing improvement
5. Rolling-horizon re-planning on cancellation

Background: this is the "satellite range scheduling" problem. The general problem with multiple antennas, slew time, and buffers is considered NP-hard, which is why heuristics are used.

## 5. OOP design (proposed)
- `Satellite` -> `CubeSat`, `WeatherSat`, `CommsSat`
- `Scheduler` interface -> `GreedyScheduler`, `DPScheduler`, `LocalSearchScheduler` (**Strategy**)
- `Constraint` interface for slew time, buffer, elevation rules
- **Observer** for conflict and cancellation alerts
- **Command** for undo/redo of schedule edits
- Factory/Abstract Factory is optional for satellite and station creation

## 7. Tech stack (proposed)
- Java 17+ (LTS), IntelliJ or Eclipse, Maven or Gradle, Git/GitHub, JUnit 5
- JavaFX for UI; Jackson/Gson for JSON, OpenCSV or plain Java for CSV
- predict4java (simpler) or Orekit (more powerful, heavier setup) for pass prediction
- Optional: JFreeChart (benchmark charts), JaCoCo (coverage), SQLite (run history), OR-Tools (stretch)
- No special hardware, paid APIs, or cloud needed. Everything runs on a normal laptop.

## 8. Data sources
**Freely available:**
- **CelesTrak:** free, no login, orbit data (GP/TLE) in JSON/CSV/XML, with ready-made groups (active, weather, stations, cubesats)
- **Space-Track.org:** official source, free account with data-sharing agreement; CelesTrak mirrors the same data
- **SatNOGS DB:** satellite and transmitter info; also lists real volunteer ground stations with coordinates
- **UCS Satellite Database:** CSV with operator, purpose, orbit class for 10,000+ satellites

**Important catch:** the 5-digit catalog number limit of the classic TLE format has been reached. New objects have 6-digit catalog numbers (100000+) and are not available in TLE format. Parse the OMM formats (JSON/CSV) instead of only two-line TLEs. CelesTrak's default format is now CSV. Check that the chosen library version supports OMM.

**Not publicly available (must be assumed or simulated):** satellite priorities, data volume per pass (estimate: downlink rate x pass duration), onboard buffer sizes, antenna slew speed and antenna count, cancellation events. Keep all assumptions in one config file or document.

**Practice:** commit a snapshot of orbit data to the repo for reproducible, offline demos; live fetch is optional and should be rate-limited.

## 9. How ground stations work (for context)
A station is an antenna on a motorized rotator plus radio equipment. Per pass: predict pass -> acquisition of signal when satellite rises above minimum elevation (typically 5-10 degrees) -> antenna tracks it, with Doppler frequency correction -> uplink (commands) and downlink (telemetry and payload data) -> loss of signal -> antenna repositions for the next pass. Small cubesats commonly use UHF/VHF; larger or imaging satellites use S/X-band. Existing setups range from manual spreadsheets (university stations), to volunteer networks (SatNOGS), to ground-station-as-a-service (AWS Ground Station, KSAT) and agency networks (NASA, ESA). Internal scheduling tools of operators are largely proprietary, so avoid claiming specifics about their algorithms.

## 10. Positioning and honest claims
- **Unique among student/hackathon projects:** yes (space-ops scheduling is rare there).
- **Not novel in research:** satellite range scheduling is an established field with commercial tools. The novelty is building and comparing algorithms ourselves.
- **Effectiveness:** no fixed "percent solved" figure should be claimed. Defensible claim: within the modeled constraints, the best algorithm improves downlinked data and priority-pass coverage by X% over a baseline across N generated scenarios (X to be measured). It covers the core scheduling decision, not full ground-station operations (no weather modeling, hardware faults, network latency, licensing).
- **UVP:** a multi-algorithm scheduler with measurable benchmark results, natural use of several design patterns, and live re-planning, on a space-ops problem few student teams attempt.

## 11. Constraints for any AI agent helping
